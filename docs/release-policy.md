# Release policy

This document is the operating procedure for cutting an AntiFl0ck release.
`GOVERNANCE.md` defines the gate; this document defines the flow, the artifact
set, the tag format, rollback, and what an external adversarial gate means.
`.github/workflows/release.yml` implements it.

## Baseline

No release-qualified tag exists. `v0.1.0-alpha` is an engineering completion
boundary and predates the current `main` gate. The first release-qualified tag
will be cut only from a `main` commit on which all eight required status
checks succeeded on that exact SHA. The release workflow checks this itself:
it resolves the tagged commit, requires it to be reachable from `origin/main`,
lists the check runs bound to that SHA, and fails unless every required
context completed with `success`. Missing, skipped, cancelled, or in-progress
checks fail the gate.

## Flow: release candidate → canary → release

1. **Release candidate.** A maintainer tags a `main` commit `vX.Y.Z-rc.N`.
   `release.yml` runs the gate, builds, generates the SBOM and checksums,
   signs, attests, and creates a **draft pre-release**. The maintainer
   verifies the bundle locally (commands below) and publishes the
   pre-release. Release candidates are for testing only and carry no support
   commitment.
2. **Canary.** The candidate runs on at least one operator-controlled lab
   host for a soak period (a minimum of 72 hours for a minor release, 24 hours
   for a patch) with the deterministic scenario and the strict acceptance
   harness passing against the built binaries, not the source tree. Any
   defect that requires a code change restarts the sequence with a new
   candidate (`-rc.N+1`); candidates are never amended in place. A
   `vX.Y.Z-canary.N` tag may be used when the canary build must differ from
   the candidate only by build metadata.
3. **Release.** The same commit as the final candidate is tagged `vX.Y.Z`.
   `release.yml` produces a fresh, independently signed artifact set and a
   draft release. The maintainer verifies the bundle, confirms the SHA256SUMS
   of the binaries match the final candidate's (same commit, same toolchain,
   `-trimpath`: they must), fills in the notes from `CHANGELOG.md`, and
   publishes. Publishing is the only manual step and is the authority-bearing
   act; a draft is not a release.

A manual `workflow_dispatch` runs the whole pipeline on any ref, uploads the
artifact set as a workflow artifact, and never creates a release, whatever
the `dry_run` input says; with `dry_run: true` gate failures are downgraded to
warnings. Only a pushed tag creates a draft release. Use the manual run to
validate the pipeline itself.

## Tag format

- `vMAJOR.MINOR.PATCH` — release.
- `vMAJOR.MINOR.PATCH-rc.N` — release candidate (pre-release).
- `vMAJOR.MINOR.PATCH-canary.N` — canary build (pre-release).

Tags are annotated, created on a `main` commit, and never moved or deleted.
A tag that must be withdrawn is left in place and superseded (see rollback).
Semantic Versioning applies from the first `vX.Y.Z` onward: a published
protobuf field or enum number, a CLI flag, an on-disk state format, or a
signed-plan semantic is a public contract, and breaking any of them is a
major version.

## Artifact set

Each release produces, for `linux/amd64` and `linux/arm64`:

| Artifact                                   | Purpose                                                  |
| ------------------------------------------ | -------------------------------------------------------- |
| `antiflock-agent_<ver>_linux_<arch>`       | node agent                                               |
| `antiflock-core_<ver>_linux_<arch>`        | core service                                             |
| `antiflockctl_<ver>_linux_<arch>`          | operator CLI                                             |
| `antiflock_<ver>.cdx.json`                 | CycloneDX JSON SBOM generated by `syft` via `anchore/sbom-action` (pinned by commit) |
| `SHA256SUMS`                               | SHA-256 of every binary and the SBOM                     |
| `SHA256SUMS.sigstore.json`                 | cosign keyless signature bundle over `SHA256SUMS`        |
| `SHA256SUMS.provenance.sigstore.json`      | cosign attestation bundle (SLSA v1 provenance predicate) over `SHA256SUMS` |

Build flags: `CGO_ENABLED=0 go build -trimpath -buildvcs=true -ldflags="-s -w"`,
Go `1.26.6` (the same version as the `Go 1.26.6` required check). The
workflow refuses to build from a dirty tree so `vcs.modified` is always
`false` in a release binary. `antiflock-sim` and the container image are not
release artifacts in this policy revision; the image remains a lab/dev
convenience built from `deploy/docker/core.Dockerfile`.

Signing is keyless: the workflow's GitHub OIDC identity is the signer. The
certificate identity is
`https://github.com/AetherAI3/AntiFlock/.github/workflows/release.yml@refs/tags/<tag>`
and the issuer is `https://token.actions.githubusercontent.com`. Anything
signed by a different identity, including a maintainer's personal key, is not
a release signature.

### Verifying a release

```sh
tag=v1.2.3
id="https://github.com/AetherAI3/AntiFlock/.github/workflows/release.yml@refs/tags/$tag"
iss=https://token.actions.githubusercontent.com

cosign verify-blob --bundle SHA256SUMS.sigstore.json \
  --certificate-identity "$id" --certificate-oidc-issuer "$iss" SHA256SUMS
cosign verify-blob-attestation --bundle SHA256SUMS.provenance.sigstore.json \
  --type slsaprovenance1 \
  --certificate-identity "$id" --certificate-oidc-issuer "$iss" SHA256SUMS
sha256sum -c SHA256SUMS
```

Verify in that order. A binary whose checksum is not in a verified
`SHA256SUMS` is not a release artifact.

## Rollback

- A release is never deleted, force-pushed, or re-tagged. Withdrawal is done
  by publishing a new patch release that supersedes it and by marking the
  withdrawn release as such in its notes and in `CHANGELOG.md`, with the
  reason and the affected versions.
- A security withdrawal also carries a GitHub Security Advisory. Exploit
  detail may be embargoed; the fact of withdrawal is not.
- Operators roll back by installing the previous release-qualified tag. The
  agent's enforcement transaction (snapshot → apply → verify → commit or roll
  back) means a failed upgrade of the agent leaves host state at the last
  verified snapshot; the release notes must say whether a state-format
  migration is one-way.
- A release candidate or canary that fails is simply never promoted; the
  pre-release stays visible as history.

## External adversarial gate ("Predator unavailable is not a pass")

The project expects an external adversarial CI gate: a job, run by an
independent system outside this repository's own workflows, that attacks the
pull request (hostile plan and manifest corpora, fuzzers, privilege-boundary
probes) and reports a status context back. The generic rule, independent of
which system provides it:

- **When configured, the gate is required.** Its context is added to the
  `main` ruleset and a release cannot proceed without it.
- **Absent is FAIL, not PASS.** If the external system does not report, times
  out, is unreachable, is unconfigured for the ref, or reports anything other
  than an explicit success for the exact SHA, the gate has failed. A missing
  check is never treated as a skipped or neutral result, and nobody may merge
  or release "because the gate did not run".
- The gate's result is bound to the SHA it evaluated, exactly like the
  required checks. Re-running on a rebased copy does not transfer.
- An operator may not disable the gate to unblock a release; removing it from
  the ruleset is a governance change recorded in `GOVERNANCE.md` with the
  reason.

`release.yml` applies the same rule to the existing required contexts today:
a context that is not `completed`/`success` on the release SHA fails the
gate. When the adversarial gate's context name is known, it is added to the
`REQUIRED_CONTEXTS` list in the workflow and to the table in `GOVERNANCE.md`
in the same pull request as the ruleset change.

## Permissions and secrets

`release.yml` runs with `contents: read` by default. Only the `release` job
holds `contents: write` (to create the draft release and upload assets) and
`id-token: write` (for sigstore keyless signing). No repository or
organization secret is used; the only credentials are the ephemeral
`GITHUB_TOKEN` and the OIDC token minted for the job. A concurrency group per
ref prevents two release runs for the same tag from interleaving, and an
in-flight release run is never cancelled.
